## 二、爬虫系统架构设计（1主2从）

实现**存储与计算分离**，核心目标：重庆主城区标讯采集延迟≤30分钟，所有配置与职责按以下要求落地，无额外调整。

### 1. 主机（Master - 2h4g）：系统大脑+数据仓库

- 运行组件：MongoDB数据库（存储全量数据）；

- 核心职责：维护标题指纹库、接收从机解析数据、执行AI商机评分与推送、响应从机指纹校验请求并返回决策结果。

### 2. 从机（Workers - 2h2g）：纯计算执行节点

- 运行组件：仅Python脚本+浏览器驱动，无本地数据存储；

- 核心职责：抓取数据并解析，通过API将数据传回主机，按业务拆分2台从机：

    - 从机A：负责**重庆主城9区核心平台**，高频轮询保障时间差优势；

    - 从机B：负责**区县平台、国铁、军采、烟草、金融**等行业站点，低频率采集。

## 三、核心采集与去重机制（指纹预检模式）

在原有“按标题去重”基础上，新增标题预处理与MD5指纹生成规则，避免格式差异导致重复采集，落地流程如下：

### 1. 唯一ID（contentId）生成算法

保留原有contentId字段，**字段值为标题清洗后的MD5值**，生成规则：

 $Unique\_ID = \text{MD5}(\text{Stripped\_Title})$ 

**Stripped_Title标题清洗逻辑**：

1. 去除所有首尾空格及中间的多余空格；

2. 去除标题中的特殊符号（【】、[]、（）、-）；

3. 统一转化为小写（若涉及英文）；

4. 核心目的：消除同一项目不同平台的标题格式微小差异，保证去重准确性。

### 2. 采集工作流（四步落地）

1. **扫描（Scan）**：从机A/B启动，抓取目标平台列表页标讯，采用翻页爬取模式（而非仅抓取前20条），优先抓取当日标讯；翻页终止条件：连续2页无今日标讯则停止翻页，每次翻页抓取当前页全部标讯的标题及对应发布时间，避免漏采（如早间集中发布多条标讯的情况）；

2. **日期判定（JudgeDate）**：从机提取标讯发布时间，统一格式为`YYYY-MM-DD`（与本规范contentId字段格式一致），对比当前系统日期，仅保留“发布日期=当前日期”的标讯，过滤非今日标讯；

3. **校验（Check）**：从机对筛选后今日标讯的每条标题，按清洗逻辑处理后计算MD5，将指纹组发送至主机；

4. **决策（Judge）**：主机查询MongoDB指纹库，指纹已存在则从机跳过，不存在则执行下一步；

5. **深度抓取（Pull）**：从机仅进入新指纹对应的详情页，抓取正文、预算等核心字段，同时精准识别标讯类型（如招标、中标、更正等），对应填写noticeType字段，解析后回传主机；字段提取需严格遵循「字段提取与过滤逻辑规则」（见下文）。

## 五、基础爬取规则（原有规则完整保留）

1. 采集范围：统一采集最近两天的数据，基于标题指纹去重，防止遗漏与重复采集；

2. 爬虫命名：必须见名知意，示例：wj-chinabiding；

3. 启动方式：唯一启动命令，格式：python  [wj-chinabiding.py](wj-chinabiding.py) / python [xxx.py](xxx.py)；

4. 页面加载要求：每个爬虫启动后，必须等待目标平台页面完全加载完成（含DOM渲染、元素加载），再执行抓取操作，禁止未加载完成即开始爬取，避免漏抓标讯内容或触发反爬；

5. 爬取要求：模拟人工翻页+间歇性休息，使用webdrivermanager管理chrome驱动，禁止硬编码chrome版本，做好失败重试与页面加载等待；

6. 数据保存：爬取一个列表条目即保存，不等待全部爬取完毕再统一保存。

7. 无头模式：所有爬虫默认启用无头模式（Headless），在后台运行浏览器，不弹出可视化窗口。

8. 随机等待：每次点击、翻页、打开详情页后，以及**每次采集完一条详情页数据后**，必须随机等待 1.5-3 秒，避免固定频率被封。

9. 模拟阅读：详情页加载后，自动执行随机滚动操作，模拟用户浏览行为。

## 六、字段提取与过滤逻辑规则说明

本规则为核心采集环节的专项判定标准，以重庆市政府采购网为核心适配平台，其他平台可参照执行，主要包含**列表页日期过滤**与**详情页金额/时间提取**逻辑，确保采集数据精准、字段填写规范。

### 一、 列表页日期过滤逻辑

用于判定某条标讯是否属于“今天”发布的最新数据，判定顺序如下（优先级从高到低）：

#### 1. 强制排除（Negative Filter）

若发布时间文本中包含以下关键词，直接判定为**过期数据**，不予采集：

- `昨天`

- `前天`

- `天前`（例如：3天前、10天前）

#### 2. 相对时间包含（Relative Include）

若发布时间文本包含以下关键词，直接判定为**今日数据**，进行采集：

- `刚刚`

- `分钟前`

- `小时前`

- `秒前`

#### 3. 绝对日期比对（Absolute Date）

若文本为标准日期格式（如 `2026-03-02`）：

- 将该日期与**系统当前日期**进行比对。

- 只有**完全一致**时，才判定为今日数据。

### 二、 详情页金额提取逻辑 (Budget/Price)

为应对不同招标公告中对“金额”描述的多样性，采用多组关键词正则匹配。系统会按以下**优先级顺序**尝试匹配，一旦匹配成功即停止：

|优先级|关键词类别|包含词汇|说明|
|---|---|---|---|
|**第1级**|**预算类**|`预算金额`、`预算总金额`、`项目预算`|最常见的政府采购金额描述|
|**第2级**|**限价类**|`最高限价`、`最高限制单价`、`最高单价限价`、`限价`|常见于竞争性谈判或磋商|
|**第3级**|**控制价类**|`采购控制价`、`控制价`|工程类项目常用|
|**第4级**|**估算价类**|`合同估算价`、`估算价`|概算或初步设计阶段常用|
|**第5级**|**通用类**|`单价`、`金额`、`价格`|兜底策略，适用于非标准表述|
**提取规则：**

- 提取范围：从“关键词”开始，一直截取到“万”或“元”单位结束。

- 包含内容：关键词 + 中间连接符 + 数字（含千分位和逗号） + 单位。

- *示例：匹配到“最高限价：990,666.70元”会完整保留该字符串，保留上下文含义。*

### 三、 详情页截止时间提取逻辑 (End Time)

用于提取项目的投标、报名或开标截止时间，支持多种文案表述：

|场景类型|匹配逻辑描述|
|---|---|
|**递交/提交**|匹配“递交”或“提交” ... 紧接着“截止时间”或“结束时间” ... 后的日期时间|
|**投标/响应**|匹配“投标”或“响应” ... 紧接着“截止时间”或“结束时间” ... 后的日期时间|
|**开标**|匹配“开标时间” ... 后的日期时间|
|**报名**|匹配“报名” ... 紧接着“截止时间”或“结束时间” ... 后的日期时间|
|**倒装句式**|匹配 日期时间 ... 后面紧跟“截止”二字|
**提取规则：**

- 优先精准提取出日期时间字符串（如 `2026年3月10日 10:00`）。

- 若无法精准提取日期，则回退提取包含关键词的完整短句以防丢失信息。

## 十、采集完成后的数据使用方案（贴合现有规范，落地可操作）

数据采集完成后，全部存储于MongoDB的yuedongData库，基于现有配置（AI商机评分、标准字段等），主要用于**商机挖掘、数据复盘、异常排查、业务落地**四大场景，具体操作如下，无需新增额外工具，直接依托现有架构即可实现：

### 1. 核心场景：AI商机评分与推送（依托主机现有职责）

- 自动执行：主机在接收从机回传的标讯数据（存入tender_data集合）后，会自动执行AI商机评分逻辑（规范中主机核心职责），无需手动干预；

- 评分依据：基于标讯字段（title、detail、budget、industry、area等18个标准字段），结合预设规则（如预算金额、行业匹配度、区域优先级等），对每条标讯进行商机等级划分（如高、中、低）；

- 推送使用：评分完成后，可按需求将高价值商机（如高预算、核心区域标讯）推送至指定终端（如业务系统、企业微信、邮件），推送逻辑可对接主机现有推送功能，无需额外开发。

### 2. 基础场景：数据查询与复盘（依托yuedongData数据库）

通过MongoDB工具查询yuedongData库，快速提取所需数据，用于日常复盘、业务分析，核心查询场景：

- 按条件筛选：基于字段筛选（如area筛选重庆主城9区标讯、createTime筛选今日/近几日标讯、budget筛选高预算项目、industry筛选特定行业标讯、noticeType筛选特定类型标讯）；

- 数据统计：统计每日/每周标讯总量、各区域/各行业标讯分布、各类型标讯占比、高价值商机占比，辅助业务决策（如重点布局区域、行业）；

- 历史追溯：因标讯数据全量存入tender_data，可随时查询历史标讯（如核对项目信息、追溯采集记录），契合“沉淀数据资产”的需求。

### 3. 运维场景：异常排查与采集优化（依托tender_datalog日志）

- 日志查询：通过tender_datalog集合，查询爬取异常日志（如验证码识别失败、数据回传失败、标讯抓取中断），定位问题原因（如平台反爬升级、脚本报错）；

- 优化调整：根据日志反馈，优化爬虫脚本（如调整反爬策略、修正日期判定逻辑）、调整采集频率（如某平台频繁封禁，可适当降低对应时段采集间隔）；

- 漏采补全：同步期（02:00-04:00）采集完成后，查询tender_data，核对当日标讯总量，若有漏采（如同步期未补全），可手动触发对应从机脚本，补充抓取。

### 4. 拓展场景：业务系统对接（贴合现有字段规范）
